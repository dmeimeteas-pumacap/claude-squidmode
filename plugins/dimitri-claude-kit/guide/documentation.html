■ Documentation

Generate docs from the code as it actually is, not from what the names suggest. Two commands, and you pick between them purely by how much you are pointing at: one thing, or a group of things.

Pick by scope The only question that matters here.

One thing

  • /document-process — a single project, service, or process.

Many things

  • /document-section — a folder, a category, or the whole codebase.

Neither

  • A unified system-level overview is a different job again, and is not part of the shipped kit.

/document-process

Produce a README-style document for one existing project, service, or process.

/document-process
Point it at one project, service, or process. No flags.

What it does

Reads the actual code and writes what the thing does, how it is wired, what it depends on, and how to run it. Because it sources from the code, it catches the cases where a component's name stopped matching its behaviour three refactors ago.

Reach for it when

Someone needs to understand a component you own. Also good before a handoff, and good on something you wrote a year ago and no longer remember.

Not for

Several projects at once — use /document-section, which orchestrates this one rather than making you repeat yourself. Also not for a cross-system overview.

Worth knowing

It reads the code, so it catches the case where a component's name stopped matching its behaviour several refactors ago. That mismatch is often the most useful thing in the output.

/document-section

Document a defined section — a set of projects, a category, a directory, or everything.

a category
"document all the AzFn services"
a directory
Point it at a folder and it works through what's inside.
everything
The whole codebase, in waves.

How it works

It orchestrates /document-process across each target rather than reimplementing it, so a single project and a group of forty produce consistent output.

Expect it to be big

Pointing it at a large codebase is a real amount of work and a real amount of tokens. Scope it to a category first and see whether the output is what you wanted before going wider.

Worth knowing

Coverage is tracked, so a later run can drain what has drifted rather than regenerating everything from scratch.

When NOT to

Not for one project — that is /document-process, which this orchestrates. Not for a unified cross-system overview; the kit ships no command for that.
